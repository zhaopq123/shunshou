## 五之三、P0 事故：批量私聊重复发送（2026-11-02 17:17）

| # | 现象 | 根因 | 严重度 |
|---|---|---|---|
| 16 | 同一条询价消息**连发 4 次给同一个卖家**（ZuX2） | ① 详情页「卖家名」用"长度 2~12 的短文本"猜，**猜到了时间戳 `17:16`**，SKIP 去重完全失效；② 每次 `back(2)` 后列表回到顶部，后续 tap 用的还是旧坐标，四次都点中同一张卡 | **P0（业务事故）** |

**教训（必须写进任何批量操作脚本）**：
1. **卖家身份不能靠猜**——必须从详情页的固定节点取（昵称与「会员名：x\*\*\*5」在同一行），或者干脆用「聊一聊」后聊天页顶部的昵称。
2. **每次动作后重新取坐标**，不许复用上一屏的坐标。
3. **发送前必须去重**：维护一个已联系集合，按**卖家昵称**判重，发一条记一条。
4. **批量发送要有总数上限 + 每条之间的确认**，不能一口气循环。

## 五之四、第二次重复发送（2026-11-02 17:37–17:45）

| # | 现象 | 根因 | 严重度 |
|---|---|---|---|
| 17 | 同一卖家在几分钟内收到 **2 条**消息（老余、智算虾米、Seanonly 各 2 条） | 我把"补发失败消息"和"追问价格"拆成两轮独立脚本，**两轮之间没有共享的发送节流**，只做了"是否联系过"的去重，没做"刚发过就别再发" | **P0（业务事故，第二次）** |
| 18 | 没有"等对方回复"的概念 | 去重维度只有「是否联系过」，缺少「上一条是不是我方、发出去多久」 | **P0** |

### 必须加进发送逻辑的三条硬规则

1. **每个会话在对方回复之前，最多只发一条。** 判断方法：打开会话，看最后一条消息的归属（左侧=对方，右侧=我方）；最后一条是我方 → 不许再发。
2. **发送节流**：同一会话 30 分钟内最多 1 条，无论内容是否不同。
3. **失败重发不算新消息**：如果上一条是「发送失败」，重发它，但重发后必须等回复，不能再追加追问。

### 29. 根治方案（治"锁屏后连不上"，只差一次连接窗口）

App 侧确认：`AgentService` 只持有前台通知，**没有申请 PARTIAL_WAKE_LOCK，也没有 /wake 接口**，
`AndroidManifest` 里虽然有 `WAKE_LOCK` 权限但从未使用 ⇒ 深度休眠后 CPU/网络被挂起，HTTP 就死了。
所以根治分两层，第一层不用改 App：

| 层 | 做法 | 效果 |
|---|---|---|
| 系统设置（一次 adb，10 秒） | `dumpsys deviceidle whitelist +com.zpq.phoneagent`、`settings put global stay_on_while_plugged_in 7`、`settings put system screen_off_timeout 2147483647`、`locksettings set-disabled true` | 电池白名单 + 插电不息屏 + 超时 24h + 免锁屏 ⇒ 顺手后台随时可连 |
| App 升级（需重编 APK） | `onServiceConnected` 申请 `PARTIAL_WAKE_LOCK`；新增 `GET /wake`（`SCREEN_BRIGHT_WAKE_LOCK or ACQUIRE_CAUSES_WAKEUP` + `KeyguardManager.disableKeyguard()`） | 即使黑屏也能被 PC 唤醒并解锁（仅限无密码锁屏） |

| 实测步骤 | 权限页点「一键关闭全部」→ 读 `settings get secure enabled_accessibility_services` → 用 adb 启动 App 再点「一键开启全部」→ 回读 |
| 关闭结果 | ✅ 生效：无障碍列表从 `carlink:phoneagent` 变成只剩 `carlink`，8712 随服务停掉；前台按队列依次跳到 `AppBatteryUsageActivity` → `NotificationFilterActivity` → 小米应用详情 |
| 关闭的坑 | ⚠️ 点完之后「下一步」靠 `onResume` 推进：每按一次返回、每把 App 拉回前台，都会再跳一个系统页，且会从电池页重新开始绕，形成**来回跳**。最后停在电池页，人不知道流程到底结束没有 |
| 开启结果 | ✅ 生效：无障碍写回 `carlink:phoneagent`，`accessibility_enabled=1`，`netstat` 里 8712 重新 `LISTEN`，`ph -d 红米 dev` 拿到 `v14-tabs`；队列最后停在小米「自启动管理」页，需手动返回 |
| 边界 | 「关闭」**不会真正撤销**电池白名单与通知权限——这两项只有系统页能改，App 只能把人送过去。文档已在 README「权限中心」注明 |
| 待改 | ① 队列改成「跳页 → 等 `onResume` 回来只推进一次」，用一次性标志位；② 流程结束时给结束提示，别停在电池页；③ 关闭前先确认当前是否在跑，避免重复入队 |

### 33. 覆盖安装后 MIUI 会把无障碍开关清掉（2026-11-03 两次复现）

| 项 | 内容 |
|---|---|
| 现象 | `adb install -r` 装完新包，`settings get secure enabled_accessibility_services` 里只剩 `carlink`，顺手消失，8712 立即不监听 |
| 根因 | MIUI 把「换包」当成新来源，沿用第 30 条的未知来源策略，把敏感权限重置 |
| 处置 | 装完立刻 `settings put secure enabled_accessibility_services '<原值>:com.zpq.phoneagent/com.zpq.phoneagent.AgentService'` 再 `accessibility_enabled 1` |
| 影响 | **每次覆盖安装都必须补这一步**，否则会误判成"新包编译坏了" |

### 34. 上传文件时客户端报「连接被意外关闭」，其实服务端已写盘成功

| 项 | 内容 |
|---|---|
| 现象 | PowerShell `Invoke-RestMethod -InFile` 报连接被意外关闭；但 `GET /files` 里文件大小完整、MD5 一致 |
| 根因 | .NET 默认发 `Expect: 100-continue`，服务端不回 100 就直接读 body，客户端等不到确认便重发/断开 |
| 修法 | `handle()` 读到 `expect` 头先回 `HTTP/1.1 100 Continue`；同时 `Caps.save` 按 `Content-Length` 精确读满，不靠 EOF（客户端发完不会关写端，等 EOF 只会白等 soTimeout） |

### 35. adb 同时存在 mDNS 名与 IP 两条连接时，命令报 `more than one device`

| 项 | 内容 |
|---|---|
| 现象 | `adb devices` 同时列出 `adb-VOZPVS5LU4U899CQ-...` 和 `192.168.3.48:38063`，不带 `-s` 的任何命令都失败 |
| 处置 | 所有 shell/install 命令统一带 `-s 192.168.3.48:38063`；别用 `adb disconnect` 去清，清了会把唯一通道也断掉 |
